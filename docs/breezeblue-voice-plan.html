04

插件这一轮改了什么

不是“换个地址和 Key”，而是在发送前替换消息链。这轮修的都是会导致真实现场翻车的地方。

改动版本原因
钩子 priority 0 → 100v0.2.0社区 ADR 实测：clonetts 默认 priority 0，两个抽签器同序会导致同一句合成两次、花两份钱。priority 100 让我们先决定，后面的插件看到 Record 就跳过。
Record 的 text 置空串v0.2.0别的 TTS 插件用 hasattr(c,"text") 收正文；text=None 会让它 "".join([None]) 抛异常，原文又会被再合成一次。
只处理 LLM 结果v0.2.0result.is_llm_result() 为假时直接返回。指令回执、工具结果、错误提示不会被念出来。
新增 use_file_servicev0.2.0AstrBot 与 NapCat 分容器时，本地路径对方读不到。开启后走 AstrBot 文件服务换成 HTTP URL，与内置 TTS 的做法一致。
voice_settings 支持v0.2.0新增 speed（保音高变速）、guidance_scale、use_speaker_boost。夜谈的“困倦/撒娇”可以靠 speed + instructions 调，不用播放端变调。
trigger_mode 真正生效v0.2.0旧版配置项 trigger_mode 是死配置，代码只读 only_explicit。现在两者取或，UI 改了就生效。
管理员测试指令v0.2.0/bbvoice test 精确发测试句，/bbvoice status 看今日用量。仅管理员，且受 allowed_groups 与额度约束。
preflight 体检脚本v0.2.0补上内置 TTS、分段、流式、callback_api_base、插件版本的只读检测。

没动的部分：聊天模型、人设、记忆、QQ 连接、消息管线顺序。插件只挂在发送前一步，改的是 result.chain，不碰 Prompt、不碰会话存储。

为什么不能“只改本地 TTS 的地址和 Key”

AstrBot 内置 TTS 走的是它自己的 Provider 抽象（OpenAI 风格 /audio/speech 或各家专用实现）。BreezeBlue 是 xi-api-key + 路径带 voice_id + voice_settings 的另一套协议，字段名、鉴权头、响应形态都不同。内置 Provider 不会因为改 base_url 就兼容。所以必须用插件在 on_decorating_result 里直接换 Record，绕开 Provider 层。

08

随机 70% 文字 / 30% 语音的真实行为

“30%”是每条回复独立抽签，不是每 10 条固定 3 条。另有三个因素会把实际比例压低或抬高。

机制行为对比例的影响
独立抽签每条 LLM 回复 random() < 0.3 才转语音20 条样本可能只有 3 条，也可能 9 条，属正常波动
会话冷却同一会话两条语音最小间隔 90 秒群聊密集时实际比例会明显低于 30%
明确索要命中“发语音 / 语音说 / 说给我听”等关键词跳过概率与冷却，100% 语音，会拉高比例
长度与媒体超过 60 字、超过 3 行、含图片/视频/文件直接保留文字，拉低比例
想真正接近 30%，把冷却调到 45 秒

按平均 20 秒一条回复估算，90 秒冷却把上限压到约 18%（20 ÷ 110）；45 秒冷却约 31%。建议群里先用 45 秒，私聊用 0（私聊节奏慢，不需要冷却）。这个值在 WebUI 里改，改完即生效。

不需要任何 /语音 指令。用户正常聊天即可；明确说“发语音”只是加速通道，不是开关。指令回执、工具消息、错误提示一律不转语音。

10

夜谈的音色为什么“还是不行”

先定位问题，再判断新音色能不能解决。否则换十个音色还是同样的毛病。

本地 edge-ttsMac 127.0.0.1:9880
8 个基础音色
播放端变调14 个 VoiceKind 靠 pitch 派生
共振峰不跟着变
AzureSSML 内做音高/语速
配置了才走
腾讯云 16 kHz窄带 mp3
仍二次变调
系统 TTS离线兜底
机械感明显

三个真正拉低听感的地方

问题机制表现
变调代替音色14 个音色只映射到 8 个基础音色，其余靠 PitchedAudioPlayer 移调。移调只改基频，不改共振峰，人耳会听成“同一个人捏着嗓子”。甜美女童 +50Hz、磁性大叔 −40Hz 最容易露馅
16 kHz 窄带腾讯云链路 SampleRate: 16000、mp3。齿音和气息被切掉，低频发闷。像电话里的声音，不像贴着耳朵说话
没有表演控制文本直接送 TTS，情绪只存在于文案里。TTS 不知道这句是撒娇还是困倦。同一句话永远同一个语气，长聊会“念稿感”

这三点里，前两点是工程问题，换音色之前就该修；第三点是能力问题，恰好是 BreezeBlue 的 instructions 想解决的。

BreezeBlue 对夜谈的结构性价值

原生 24 kHz 单声道；speed 变速保音高，不需要播放端移调；instructions 用自然语言给表演方向（“年轻女声，轻一点，像临睡前贴着耳朵说话”）；guidance_scale 控制贴程度。这四点是现有 edge-tts + 变调链路给不了的。

11

voc_8yud7hz7c9q2 是否适配夜谈

现在不能下结论。能下的是判定标准和试听方法；听完按表打分，结论自然出来。

为什么不能现在判断

没有 Key，查不到这个 Voice 的 language_code / gender / age / tone / accent，也生成不了样音。仅凭 ID 猜性别、年龄、音色是耍流氓。任何“听起来应该不错”的说法都不作数。

夜谈需要什么样的声音

夜谈是睡前陪伴场景，不是播客也不是客服。权重按这个场景定：

维度权重判断点及格线
音色本体25性别、年龄、气质是否贴主推角色；是否“像一个具体的人”而不是播音员年轻女声 / 温润或清冷
亲密距离感20有没有气声、软起音；会不会太亮、太冲、太“营业”像贴着耳朵说话
情绪可塑性20同一句能否演出撒娇、困倦、吃醋、安慰四种状态四种可分辨，不崩
普通话与咬字15是否标准普通话；有无方言尾音；轻声/儿化是否自然无口音，吐字清楚
低音量外放10手机外放 30% 音量，夜里听是否清楚、是否刺耳字字可辨，不炸耳
稳定性与延迟1020 句里有没有破音、漏字、突然变速；首字节到出声多久无明显故障，<2s

判定：≥80 分进 P1；65–79 分只用于长音频/高光时刻；<65 分不进 App，只留在 QQ 侧。这组阈值先定死，避免听完“感觉还行”就上。

盲测流程（30 分钟）

  1. 准备三条链路：BreezeBlue voc_8yud7hz7c9q2、夜谈当前线上音色（本地 edge-tts 或 Azure）、系统 TTS。
  2. 同一组 6 句台词，三条链路各生成一遍，文件重命名成 A/B/C 打乱顺序，不看来源。
  3. 先手机外放 30% 音量听一遍，再戴耳机听一遍；每次只记分，不猜是谁。
  4. 找 2 个不知情的人各听一遍，取平均分。自己听容易先入为主。
#台词考什么
1呜哇，被你发现啦! 我在认真思考呢，才没有摸鱼。轻快、上扬、气声
2你今天怎么这么晚才回来，我等你好久了。埋怨但不凶，尾音软
3别闹了……我困了，你抱着我说会儿话好不好。困倦、低音量、拖音
4哼，我才没有吃醋，你爱跟谁聊跟谁聊。口是心非，重音位置
5没事的，慢慢来，我一直在这儿。安慰，语速放慢
6（笑）你这个笨蛋，连这个都记不住。笑声、亲昵、不刻薄

第 3、4、6 句是分水岭。多数 TTS 能把第 1 句念好，但一到“困倦”“口是心非”“带笑的骂”就露出念稿感。如果这三句也能过，这个音色才值得进夜谈。

如果音色不合适，怎么换

不要直接换 ID 硬试。先按第 10 节修工程问题（去掉播放端移调、换 24 kHz），再用 tools/audition.py 按 gender / age / tone 筛候选，preview 不计费，选定 5 个候选再用同一句付费对比（5 × 24 字符 ≈ 21.5 credits）。

夜谈接入路线

QQ 和 App 用同一个音色，角色在两个端听起来才是同一个人。但通话和语音条要走不同引擎。

阶段做什么产出 / 门槛成本
P0试听与盲测，不改代码6 句 × 3 链路，评分表；决定“进/不进”< 10 credits
P1AstrBot QQ 侧上线，测试群灰度30% 语音、额度 30、失败回退文字；G0–G4 全过约 $4/月
P2夜谈 App 加 BreezeVoiceClient，只给 1 个主推角色语音条按需合成，缓存 + 日预算；通话仍走本地/Azure按用量
P3角色音色库 + 表演预设每个角色一个 voice_id + 一套 instructions（撒娇/困倦/安慰/调侃）按用量

P2 的工程边界

  • 新增 Core/Voice/BreezeVoiceClient.swift，签名与现有 TencentTTSClient.synthesize(text:kind:) 对齐，不改 VoiceService 的调用方。
  • Key 存 Keychain，与现有 LocalSecrets 一致；不进 UserDefaults、不进日志、不进崩溃上报。
  • 角色模型加可选 breezeVoiceID；为空就走现有链路，零迁移成本。
  • 只在“点语音条播放”时调用，不在每条回复后自动合成。通话要的是低延迟，云端表达型 TTS 不适合实时对话。
  • 日预算 + 失败回退：超预算、超时、401/429 一律回退现有音色，不弹错、不静默失败。
为什么通话不换

通话是“说完就要接上”，云端同步合成 1–3 秒的等待会直接破坏节奏。现有本地 edge-tts 首字节更快，虽然音色差，但通话体验优先。把 BreezeBlue 放在“语音条/高光时刻/分享”这类可以等的场景，收益最大、风险最小。
