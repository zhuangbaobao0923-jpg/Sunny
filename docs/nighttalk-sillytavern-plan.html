产品分析 · 2026.11.23

把酒馆的玩法，
拆成手机上的三个按钮

SillyTavern 值得抄的不是它的插件市场，是它把一段对话拆成了六层可组装的协议。 夜谈不必把控制台搬到手机上——该搬的是这些协议在消费级产品里最终呈现的结果。

01

先纠正一个直觉

SillyTavern 是"给折腾党的前端"，夜谈是"给普通人的产品"。这两者的差异不是功能多少，是成本由谁承担、控制权交给谁。

结构差异

它拆协议，我们写模板

ST 把一次对话拆成卡、书、预设、正则、摘要五份可替换的文件。夜谈把这些全部写死在 PersonaPrompt.swift 的 100 行里。前者能长生态，后者只能长功能。

成本差异

它烧用户的钱，我们烧自己的

ST 用户自带 API Key，所以可以无限重抽；我们每 roll 一次都是真实成本。这直接决定了 swipe 必须做成"一次出两条候选"，而不是"点一次抽一次"。

机会差异

有三样东西它永远做不到

语音通话、推荐流发现、亲密度成长。ST 是桌面工具，没有麦克风场景，没有"刷到一个人"，也没有关系进度。玩法必须长在这三样上。

ST 的六层里，夜谈只搭了半层卡、一层记。
但夜谈有的那三样，ST 一层都没有。

02

六层拆解：用户到底买什么

把 ST 的功能按"用户的真实动机"重排，而不是按它的菜单排。左边是机制，中间是心理，右边是夜谈的现状。

层ST 的机制用户买的是夜谈现状判断
卡 Character Card V3（.charx），PNG 内嵌 JSON，备用开场白，可内嵌世界书 收集与收藏，角色是资产 Character 散字段：name / tags / bio / opening / replies 借格式，不借编辑器
书 World Info：关键词触发、递归激活、可绑定角色或人设或单个聊天 世界可信，不会前后矛盾 无。记忆只是最近 3 轮的时间轴 必做，但要换个名字
群 Group Chat：多卡同场，轮流 / 自然 / 列表三种发言规则，成员可静音 场面感与意外 无。永远一对一 差异化最大，语音版是护城河
记 Summarize 自动摘要、Vector Storage 向量检索、Data Bank 文档 RAG 关系连续，"她记得" 72 小时承接问候 + 最近 3 轮注入，每条截 40 字 最影响留存，优先级最高
控 Presets、Advanced Formatting、Author's Note、Regex、STscript 品味表达，"这是我调的" 硬编码在 PersonaPrompt.system 降维成后台参数，不暴露给用户
变 Swipe 重抽、Branch 分支、Checkpoint 存档点 后悔药 只有失败重试（ChatModel.retry），成功的那句无法重来 最便宜的高回报
一个容易被忽略的点：ST 的"控"层看着最唬人，其实是最不该搬的。它存在的理由是用户要用各种奇怪的模型、要压榨每一分上下文。 夜谈只有一个模型、一种调性，把这层的价值转成我们自己的运营手感就行——傲娇角色 temperature 给 0.9，回忆场景压到 0.6， 用户不需要知道这些词。

04

三个玩法，都是按钮不是面板

每个都对应 ST 的一层，但界面只留一个动作。用户永远不需要知道"世界书""swipe""group chat"这些词。

P0

换个说法

对应 Swipe · 1–1.5 天
现状
只有失败重试。回复一旦成功落库，用户不满意只能自己再发一句"重说"——这本身就破坏了沉浸感。
做法
长按 AI 气泡 → 「换个说法」。气泡右上角出现 1/2，左右滑切换候选，选中的那条才进历史。原句保留，随时能切回。
关键决定
一次请求直接出 2 条候选（n=2），而不是点一次抽一次。ST 用户花自己的 token 可以无限 roll，我们花自己的钱。每轮上限 2 次，会员可放开。
改动点
ChatMessage 加 alternatives:[String] 与 altIndex；ChatHistoryStorage 的快照编码要兼容旧数据（缺字段时按单条处理）。
为什么先做
它是"控制感"的最小单元。用户第一次发现"我不喜欢这句可以换掉"，对产品的信任会立刻不一样，而且它不改任何已有架构。
P1

她记得

对应 World Info · 3–4 天
现状
PersonaPrompt 只注入 memory.suffix(3)，每条截断 40 字。三周前说过的猫，第四轮就永久消失。不是模型记不住，是我们没给它。
做法
记忆从"滚动窗口"改成"条目库"：LoreEntry{ keys, content, weight, source }。读取时扫最近两条用户消息，命中就把条目拼进 prompt；weight 高的（关系设定、称呼）常驻。
写入策略
不是每轮都写。规则层用现成的 ChatText.salientKeyword 抓"名字、约定、偏好、事件"，每 8 轮再用小模型抽一次。写多了会变成流水账，写少了等于没有。
UI 是什么
不做 ST 那种表格编辑器，做「TA 的记事本」：一页纸，列出她记住的事，可以划掉、可以补一句。这比参数面板动人得多——用户第一次看见"她把我说的记住了"这件事被具象化。
顺带的好处
条目比原始对话短得多，同样的预算能装十倍信息量。做对了，上下文成本反而下降。
P2

同一个屋檐

对应 Group Chat · 文字 3 天 / 语音 7 天
现状
永远一对一。没有"人物之间有关系"这件事，也就没有场面。
文字版
2–3 个角色同一会话。输出约束成 【名字】内容，前端解析后分气泡、分颜色。没说话的人保持"在场"，会对他人的话有反应。
语音版
复用 VoiceCallView 里现成的沉默调度（25 秒轻问 / 45 秒碎碎念）和 CallScripts 的台词池，把触发条件从"用户沉默多久"换成"被点名 / 情绪高 / 沉默 8 秒"来决定谁开口。抢话和打断本身就是戏，这是 ST 结构上给不了的东西。
风险
模型忘记前缀的概率不低。必须做容错：整段没前缀就归给主角色，多于一个前缀就按第一条切。不要把解析失败暴露成报错。
为什么值得
这是唯一一个"用户会截图发给朋友"的玩法。推荐流解决发现，群聊解决传播。
还有一个几乎零成本的：ST 的 Author's Note（在对话深度处插一句导演指令）。 换成夜谈的说法就是「场景卡」：雨夜、医院走廊、生日、停电。用户点一下，系统注入一段氛围指令和一条世界书条目。 UI 只是一个横向滑条，但沉浸感提升比很多大功能都明显。可以挂在 P1 里顺手做掉。
05

真正的内核是上下文预算

ST 最值钱的不是界面，是它对"这一段对话里每一分 token 该给谁"的管理。夜谈现在三处硬编码，等于没有预算概念。

段夜谈现状建议预算策略
系统规则 PersonaPrompt 硬编码 9 条 ≈300 token 固定。通话与文字两套已经分开，保持
角色卡 bio + 3 条 replies，无上限 ≈500 token 超预算时按段落截断，优先保人设与语气样本，砍外貌描写
世界书命中 不存在 ≈400 token 按 weight 排序填，装不下就丢低优先级的，宁可少不可乱
记忆 suffix(3) + 每条 40 字 ≈300 token 改成摘要 + 条目。超过 30 轮滚动压缩成一段第三人称回顾
对话历史 historyWindow = 20 剩余全部 从新往旧填，满即停；不再用固定条数
用户输入 — 最后插入 保证它是 messages 的最后一条（现有逻辑已正确）
成本提醒：三个玩法都会推高单用户成本。重抽 +60%，群聊 +150%（多角色各自的人设都要进 context）， 记忆条目反而 −20%。整体大概翻一倍。要么按角色定价，要么把重抽和群聊做成会员能力——这件事要在做之前定，不能做完再补。
06

明确不做的五件事

克制比补齐更重要。这些在 ST 里都成立，在手机上都站不住。

插件系统生态移动端没人装插件，审核也过不去。要做就做"一键套用"，不做开放扩展。
采样参数面板控制temperature / min-p / 上下文长度，用户看不懂也不需要。收进后台按角色预设。
正则脚本编辑器清洗输出清洗该在服务端预置好（去 AI 腔、去括号动作），不该让用户写正则。
本地模型接入算力手机跑不动 7B，跑得动的那点质量会毁掉体验。已有云端可换模型就够了。
世界书表格编辑器形态行列 + 触发词 + 优先级，是工程师的界面。换成"记事本"叙事形态。
无限重抽成本ST 用户花钱，我们烧钱。限次 + 会员，否则一个用户能把毛利抽穿。
07

落地顺序

先做能被感知的，再做能被传播的，最后做能收钱的。每一步都不推翻上一步。

第一周
换个说法
改 ChatMessage + 气泡交互 + n=2 请求。旧数据兼容，可回滚。
第二、三周
她记得
条目结构 + 扫词注入 + 记事本页面。同时把 context 改成预算制。
第四周起
同一个屋檐（文字）
输出格式约束 + 多气泡归属 + 说话人调度。跑通后再评估语音版。
一季度
剧本包
云端 agents 表扩 card_json / lorebook_json / 价格。卡 + 书 + 语音 + BGM 一起卖。
三个要提前想清楚的风险： ① UGC 卡的审核——现在 published 只是一个布尔值，没有审核流，卡一旦能带世界书，擦边内容的面积会变大； ② 卡版权——用户导入别人的卡，需要来源字段与下架机制； ③ 语音群聊的打断逻辑——多人同时说话，AVAudioSession 和 TTS 队列都要重排，这块是真正的工程量。
